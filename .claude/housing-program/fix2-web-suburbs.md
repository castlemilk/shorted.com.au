### 3. [MINOR] The new `next:{revalidate:86400}` tag cannot cache the resolution fetch — the payload is over Vercel's 2 MB data-cache limit
**Where:** web/src/app/actions/getHousing.ts:45-46

**What's wrong:** `suburbIsrFetch` is applied to `listStateSuburbs` (line 132), which is the slug->SAL resolution path for every suburb render. Measured against prod today: NSW 3,355,213 bytes / 816 ms, QLD 2,406,644, VIC 2,344,439 (4,544 / 3,235 / 3,076 rows). Next stores fetch-cache entries as base64 inside a JSON envelope and hard-drops anything over 2 MB — `node_modules/next/dist/server/lib/incremental-cache/index.js:382-391` (`if (ctx.fetchCache && !hasCustomCacheHandler && itemSize > 2*1024*1024) { ...; return; }`), with the failure swallowed by the `catch` in `patch-fetch.js:475`. So for all 8 states the write is silently discarded and nothing is ever read back. The tag is still load-bearing (without it `serverFetchWithUserAgent` forces `cache:'no-store'` on the POST and throws DynamicServerError during static generation), but the comment ("These requests must be explicitly cacheable") and the new test (`getHousing.test.ts` "marks suburb list and profile RPC fetches as ISR-cacheable") assert only that the tag is passed, not that anything is cached. Net effect: each of the 15,345 suburb URLs re-downloads its entire state on every ISR (re)generation. The sibling `web/src/app/housing/[state]/[suburb]/opengraph-image.tsx` amplifies it — it exports `revalidate = 86400` but has no `generateStaticParams`, so per the project's own recorded landmine ("Dynamic segment ISR requires generateStaticParams to EXIST (even returning []) — without it revalidate is inert, route renders per-request") it runs the same full-state pull on every single card fetch.

**How it fails:** Googlebot crawls the 1,165 priced suburb URLs plus their OG cards after a revalidate window expires. Each page generation issues a fresh 2.3 MB ListStateSuburbs, and each OG fetch issues another one uncached — roughly 3-5 GB of Cloud Run egress and ~800 ms added to every cold TTFB, for a lookup that needs one row. A full 15,345-URL crawl is ~38 GB.
